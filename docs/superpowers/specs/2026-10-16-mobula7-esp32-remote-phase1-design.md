# Mobula7 + ESP32 — שלב 1: אב-טיפוס שולחני לשליטה מהאייפון

תאריך: 2026-10-16 · סטטוס: טיוטה לאישור

## הכוונה, ולמה

להחזיר לטיסה רחפן Happymodel Mobula7 ישן, ולהטיס אותו בשלט שנבנה במיוחד בשבילו מחלקים שכבר יש בבית: שני לוחות ESP32 וכפתורי מקלדת, כשהאייפון משמש כמקלות וכמסך. הטיסות שהמשתמש מתכנן הן טיסות קצרות ונינוחות בתוך הבית, וטיסה קרובה וקלה בחוץ.

המשתמש ביקש לבנות את הפרויקט בשני שלבים. **בשלב 1 (המסמך הזה) מוכיחים על השולחן שהכול עובד**, ורק אחר כך מדפיסים: הטלפון מתחבר, הרחפן מתרומם, וה-ESP32 שולט בו. השלט המודפס (סקיצה A, "ידיות קונסולה") יקבל מסמך תכנון נפרד, וייכתב רק אחרי שהשלב הזה יצליח.

## הגדרת הצלחה

הרחפן מרחף בגובה נמוך בחדר, וה-ESP32 מחובר אליו. מטיסים אותו ממקלות וירטואליים במסך האייפון. לחיצה על כפתור KILL פיזי מכבה את המנועים מיד. גם ניתוק של הטלפון, של השלט או של הקשר האלחוטי מכבה את המנועים.

## מטרות

1. קוד ל-ESP32 של השלט ("TX"): יוצר רשת Wi-Fi, מגיש לאייפון דף שליטה, קורא את כפתורי ARM ו-KILL, ומשדר ב-ESP-NOW.
2. קוד ל-ESP32 של הרחפן ("RX"): מקבל ESP-NOW ומוציא iBUS לבקר הטיסה.
3. דף שליטה לאייפון, ב-Safari, בלי התקנת אפליקציה: שני מקלות, מצב קשר, מצב חימוש, וכפתור BEEP במסך.
4. בלוק פקודות CLI אחד ל-Betaflight שמגדיר את הלוח לקבל את הפקודות מה-ESP32.
5. מדריך בדיקות מדורג בעברית, מבדיקת בריאות ועד ריחוף ראשון, עם סכמת חיווט.

## לא בשלב הזה

- השלט המודפס, תושבת מודפסת לרחפן, ותופסן הטלפון המתכוונן.
- טלמטריה מהרחפן (מתח סוללה וכדומה) על מסך הטלפון.
- שליטה בהטיית הטלפון. המשתמש אמר שאין בזה צורך כרגע.
- מצבי טיסה מלבד Angle, כלומר בלי כפתור MODE פיזי.
- וידאו או FPV.
- עדכון firmware של Betaflight, או שינוי של PID ו-rates.
- בדיקת טווח בחוץ.

## מה אסור שיקרה (גם אם "זה עובד")

- **הרחפן מתחמש בלי שהתכוונו לכך.** זה כולל חימוש אוטומטי כשמחברים סוללה, חימוש בגז גבוה, או חימוש מחדש אחרי KILL בלי לחיצה מכוונת.
- **מנועים ממשיכים להסתובב** אחרי KILL או אחרי אובדן קשר בכל אחת מהחוליות.
- דרישה להתקין אפליקציה, או לחבר את הטלפון לאינטרנט.
- שינוי ערכי הכיול של הרחפן (PID ו-rates).

## מה ידוע על החומרה (נבדק בשיחה)

**רחפן:** Happymodel Mobula7 (שלדת 75 מ"מ) עם 4 מנועי Happymodel SE0802 **16000KV**. המשתמש אישר את זה מהסימון על המנועים, והם מתאימים ל-2S.

**בקר טיסה: Crazybee F4FR Pro V2.0**
- הלוח מסומן "CrazyBeeF4FR V2.0".
- גרסת Betaflight: `4.0.6 CRAZYBEEF4FR (C4FR), MSP API 1.41`.
- מתחבר למחשב דרך app.betaflight.com. ה-app מזהיר שהגרסה ישנה, ומחליטים לא לעדכן.
- הג'יירו תקין: הדגם התלת-ממדי זז כשמזיזים את הלוח.
- המקלט הפנימי (FrSky SPI) צומד בעבר לשלט אחר (`frsky_spi_tx_id = 121,43`).

**הגדרות רלוונטיות מתוך `diff all`:**
- `serial 0 2048 …` ו-`serial 1 2048 …`: שתי יציאות ה-UART מוגדרות ל-SmartAudio. משדר הווידאו כבר לא קיים.
- `map TAER1234`.
- `aux 0 0 0 900 1150 0 0`: ARM פעיל כש-AUX1 **נמוך**. זה מסוכן, וההגדרה מוחלפת.
- `aux 1 1 1 900 1150 0 0`: ANGLE פעיל כש-AUX2 נמוך.
- `aux 2 13 2 1825 2100 0 0`: BEEPER פעיל כש-AUX3 גבוה.
- `vbat_max_cell_voltage = 450`, מתאים לסוללות HV. `small_angle = 180`. `motor_pwm_protocol = DSHOT300`. מצב AIRMODE כבוי.

**פדים, לפי צילומים קרובים:**
- **T2 ו-R2** (UART2, ליד שקע ה-Micro-USB): פנויים.
- **R1:** פנוי, אבל לא בשימוש.
- **ארבעה פדים בקצה הלוח:** עליהם מולחמים שאריות חוטים שחור, אדום וכחול של המצלמה ומשדר הווידאו. **לא ידוע אם החוט האדום מספק 5V או VBAT, ואין מולטימטר.** לכן לא משתמשים בו.
- **החוט הירוק:** מחבר שתי נקודות על הלוח, כנראה תיקון של בעלים קודם. לא נוגעים בו.
- **אזור שנראה שרוף** בצד התחתון ליד פינה. המשתמש לא יודע מה קרה שם. בדיקת המנועים היא שתגלה אם בקרי המנועים (ESC) ניזוקו.
- **באזר** מולחם בצד התחתון ונשאר במקומו.
- **אנטנת המקלט הפנימי** (חוט שחור): לא נוגעים בה.

**מתח:** צמה של 2S, שתי סוללות 1S בטור, עם חוטים אדום, כחול ושחור ושני מחברי PH2.0. הלוח מקבל רק את החוט האדום ואת השחור.

**סוללות:** כולן 1S HV עם מחבר PH2.0, וכולן טעונות.
- 2 סוללות AHTECH Infinity 450mAh, בערך 12 גרם כל אחת.
- בערך 8 סוללות Tattu R-Line 300mAh, בערך 8 גרם כל אחת.
- **תמיד מחברים לצמת ה-2S זוג זהה: 300+300 או 450+450.** לא מערבבים גדלים. (ההחלטה שלי:) לטיסות עם ה-ESP32 על הרחפן מעדיפים זוג 300+300, כי הוא קל ב-8 גרם.
- לא אושר במפורש שיש מטען, אבל הסוללות טעונות.

**שני לוחות ESP32-WROOM-32D DevKit (HW-394, 30 פינים, USB-C).** משקלם בערך 9 עד 10 גרם עם הפינים.
- הרגולטור לא זוהה: ליד ה-USB לא נמצא סימון, מלבד "HW-39…" על הלוח עצמו. **המשתמש החליט להמשיך ולקבל את הסיכון** שה-ESP32 יישרף מהזנה ב-2S.
- את ה-VIN מזינים לפין **`VIN`**, ולא ל-`3V3` ולא ל-`VN` (VN הוא GPIO39).
- GPIO17 מסומן על הלוח של המשתמש `D17`.

**כלים:** יש מלחם. אין מולטימטר.

**טלפון:** iPhone Air (iOS 26, Safari). חובה שיעבוד גם בטלפונים אחרים עם דפדפן מודרני.

## הארכיטקטורה (הוחלט בשיחה)

```
iPhone (Safari)
   │  Wi-Fi: רשת AP של ה-ESP32, HTTP + WebSocket
   ▼
ESP32 "TX" (בשלט) ── כפתורים: ARM, KILL ── LED מצב
   │  ESP-NOW, ערוץ Wi-Fi קבוע
   ▼
ESP32 "RX" (על הרחפן)
   │  UART, iBUS 115200 8N1, GPIO17 → R2
   ▼
Crazybee F4FR, UART2 (serial 1) ── Betaflight 4.0.6
```

## חיווט

**ESP32 RX אל Crazybee:**

| ESP32 RX | Crazybee F4FR V2.0 |
| --- | --- |
| TX2 / GPIO17 | פד R2 |
| GND | פד המינוס של הסוללה (חוט שחור עבה) |
| VIN | פד הפלוס של הסוללה (חוט אדום עבה) |

- הזנה מ-VBAT ולא מהחוט האדום של המצלמה. זו החלטה שהתקבלה בשיחה, כי אין מולטימטר. 2S HV מלא הוא 8.7V, וזה בתוך התחום של הרגולטור, שיתחמם במידה סבירה.
- **כלל לשולחן:** כשה-ESP32 מחובר ב-USB למחשב, מחברים לרחפן רק את GND ו-TX, ולא את VIN.

**ESP32 TX:**
- מוזן מ-USB: מטען, Power Bank או מחשב.
- ARM ו-KILL הם כפתורי מקלדת, מחוברים בין GPIO ל-GND עם pull-up פנימי.
- בשלב 1 הכפתורים מחוברים במטריצת חיבורים (breadboard) או בחוטים מולחמים.
- (ההחלטה שלי:) ARM על GPIO 25 ו-KILL על GPIO 26. LED המובנה ב-GPIO 2 משמש לחיווי מצב.

## התנהגות: ערוצים, חימוש וכיבוי

**ערוצי iBUS** (ההחלטה שלי): הסדר AETR, והערכים בטווח 1000 עד 2000.

| ערוץ | תפקיד | מקור |
| --- | --- | --- |
| 1 | Roll | מקל ימני, ציר אופקי, חוזר למרכז |
| 2 | Pitch | מקל ימני, ציר אנכי, חוזר למרכז |
| 3 | Throttle | מקל שמאלי, ציר אנכי, **לא** חוזר למרכז. מתחיל ב-1000 |
| 4 | Yaw | מקל שמאלי, ציר אופקי, חוזר למרכז |
| 5 (AUX1) | ARM | 2000 כשחמוש, 1000 אחרת |
| 6 (AUX2) | ANGLE | תמיד 1000 בשלב 1 |
| 7 (AUX3) | BEEPER | 2000 כשכפתור BEEP במסך לחוץ |
| 8 עד 14 | לא בשימוש | 1500 |

הפריסה היא Mode 2 (הוחלט בשיחה).

**חימוש:** מצב "חמוש" נשמר ב-TX.
- לחיצה על ARM מעבירה למצב חמוש רק אם כל התנאים מתקיימים:
  - הגז במסך נמוך מ-1050;
  - הטלפון מחובר;
  - KILL לא לחוץ;
  - לא היה KILL מאז הלחיצה הקודמת על ARM.
- לחיצה נוספת על ARM לא מנטרלת את החימוש. ניטרול נעשה רק דרך KILL.
- (ההחלטה שלי:) כדי למנוע חימוש מלחיצה מקרית, צריך להחזיק את ARM לחוץ חצי שנייה.

**KILL ואובדן קשר:** בכל אחד מהמקרים הבאים המנועים נעצרים.

| אירוע | תגובה |
| --- | --- |
| לוחצים על KILL | הגז יורד ל-1000 ו-AUX1 ל-1000 מיד. כדי לחמש שוב צריך לשחרר את KILL וללחוץ שוב על ARM |
| ה-TX לא מקבל עדכון מהטלפון יותר מ-300ms | כמו KILL |
| ה-RX לא מקבל חבילת ESP-NOW תקינה יותר מ-150ms | **ממשיך לשלוח iBUS תקין עם גז 1000 ו-AUX1 = 1000.** Betaflight מנטרל את החימוש מיד, בלי השהיית ה-failsafe. (ההחלטה שלי, אחרי בדיקת הבונה. אם היו מפסיקים לשלוח iBUS, Betaflight 4.0 היה משאיר את הרחפן חמוש עם מנועים בסיבוב סרק עוד כחצי שנייה) |
| הקשר חוזר אחרי ניתוק | ה-RX ממשיך לשלוח AUX1 = 1000 עד שהוא מקבל מה-TX חבילה שבה AUX1 = 1000. אין חזרה ל"חמוש" בלי לחיצה חדשה על ARM |
| ה-RX עצמו מת או מתנתק מ-R2 | Betaflight מפעיל failsafe: `failsafe_procedure = DROP` ו-`failsafe_delay` מינימלי. בחלון הקצר הזה המנועים עלולים להסתובב בסיבוב סרק. זה ידוע ומקובל |

**תקשורת:**
- (ההחלטה שלי:) ה-TX משדר ESP-NOW בשידור לכל המקלטים (broadcast) בקצב של בערך 50Hz.
- כל חבילה מכילה:
  - מזהה קבוע ("magic") ומספר גרסה;
  - מספר רץ;
  - 14 ערוצים;
  - checksum.
- ה-RX מתעלם מחבילה שאין בה המזהה הנכון או שה-checksum שלה שגוי.
- ה-RX שולח מסגרת iBUS תקנית (32 בתים) כל 7 עד 10ms, עם הערכים האחרונים שקיבל, אבל רק כל עוד הקשר תקין.
- ה-AP וה-ESP-NOW עובדים על אותו ערוץ Wi-Fi קבוע ב-TX, וה-RX מכוון לאותו ערוץ.

**דף השליטה:**
- כתובת קבועה: `http://192.168.4.1`. בלי אינטרנט ובלי משאבים חיצוניים, כי הכול מוגש מה-ESP32.
- המסך בתצוגת רוחב. שני מקלות שתומכים במגע של כמה אצבעות במקביל.
- הדף שולח את מצב המקלות ב-WebSocket בקצב של בערך 50Hz.
- מוצג בדף: מצב קשר לטלפון ולרחפן (אם ה-TX יודע), מצב חמוש או לא חמוש, וכפתור BEEP.
- הדף מונע גלילה, זום ובחירת טקסט, כדי שמגע במסך לא יזיז את הדף.
- גם לחיצה על "חמוש" בדף לא מחמשת. **החימוש נעשה רק מהכפתור הפיזי.**

## Betaflight: בלוק CLI (ההחלטה שלי, לבדוק מול 4.0.6)

הבלוק מודבק אחרי גיבוי `diff all`. הגיבוי כבר נשמר אצל המשתמש.

```
feature -RX_SPI
feature RX_SERIAL
serial 0 0 115200 57600 0 115200
serial 1 64 115200 57600 0 115200
set serialrx_provider = IBUS
map AETR1234
aux 0 0 0 1700 2100 0 0
aux 1 1 1 900 1300 0 0
aux 2 13 2 1700 2100 0 0
set failsafe_procedure = DROP
set failsafe_delay = 1
save
```

מה הבלוק עושה:
- מכבה את SmartAudio ב-UART1.
- מעביר את UART2 ל-iBUS.
- מגדיר ARM על AUX1 **גבוה**.
- מגדיר ANGLE על AUX2 נמוך.
- מגדיר BEEPER על AUX3 גבוה.
- מגדיר failsafe שעוצר את המנועים.

את שמות ה-features ואת התחביר של `serial` ו-`aux` צריך לוודא מול CLI של 4.0.6 (`help`, `feature list`), לפני שמגישים את הבלוק למשתמש.

## סדר הבדיקות

1. **בדיקת בריאות:**
   - ✅ בוצעו: חיבור USB, ג'יירו, `version`, גיבוי.
   - נשאר: לשונית Motors, עם הפרופלורים מורדים, שתי הסוללות בצמה, וכל מנוע בנפרד בקצת גז. **מנוע שלא מסתובב עוצר את הפרויקט** עד שמבינים למה.
2. **RX על השולחן:**
   - צורבים ל-ESP32 RX קוד בדיקה ששולח ערכים קבועים או משתנים לאט.
   - מחברים GND ו-TX ל-R2, וה-ESP32 מוזן ב-USB.
   - מגישים את בלוק ה-CLI.
   - בלשונית Receiver רואים את הערוצים זזים.
3. **TX ודף השליטה:**
   - האייפון מתחבר לרשת של ה-TX ופותח את הדף.
   - הזזת המקלות מזיזה את הערוצים בלשונית Receiver.
   - ARM ו-KILL משנים את AUX1.
4. **בדיקות ניתוק, עם פרופלורים מורדים ובחימוש:**
   - כיבוי ה-TX;
   - סגירת הדף או נעילת הטלפון;
   - לחיצה על KILL.
   - בכל אחת מהן המנועים צריכים להיעצר. Betaflight 4.0 מוסיף השהיה של failsafe, ואת הזמן הזה צריך לתעד.
5. **שקילה והרכבה:**
   - מקצרים או מסירים את הפינים של ה-ESP32 RX.
   - שוקלים את הרחפן אם יש משקל מטבח.
   - מצמידים את ה-ESP32 עם סרט דו-צדדי ואזיקון, רחוק מהפרופלורים.
   - מלחימים VIN ו-GND לפדים של הסוללה.
6. **ריחוף ראשון:**
   - חדר פתוח, פרופלורים מורכבים, גובה של כחצי מטר.
   - המטרה: לבדוק שהרחפן מתרומם ונשלט. אם הוא לא מתרומם, מתעדים עד כמה גז הוא הגיע.
